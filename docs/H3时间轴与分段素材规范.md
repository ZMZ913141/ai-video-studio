## 一、能引用的变量（提示词里可写）

| 写法 | 指什么 |
|---|---|
| `<Picture 1>` ~ `<Picture 9>` | 本段第 N 张参考图 |
| `<Video 1>` ~ `<Video 3>` | 本段第 N 段参考视频 |
| `<Audio 1>` ~ `<Audio 3>` | 本段第 N 段参考音频 |

源码出处：`_create_prompt_media_bundle()` → `{"kind":"image","label":f"<Picture {index}>}`，
`_reference_manifest()` 里生成 `<Picture N> = 文件名` 的对照表。

## 二、★ 最关键的一条：`<Picture N>` 是**段内**重新编号

源码原话（`_timeline_for_prompt_index` 的 docstring）：

> "independent images and audio are filtered and ordered per segment;
> all downstream Picture/Audio labels therefore **restart from one** automatically."

意思是：**每一段生成前，插件会按该段的 `images` 列表重新筛一遍图，
然后从 1 开始重新编号。**

推论（对我们极重要）：

```
段1 images = ["main"]        →  <Picture 1> = 人物静帧
段2 images = ["shop"]        →  <Picture 1> = 门店照   ← 还是写 Picture 1！
段3 images = ["main","shop"] →  <Picture 1> = 静帧，<Picture 2> = 门店照
```

**提示词骨架一个字都不用改。** 我们 `gen_video.py` 的英文骨架里写死的
`<Picture 1>`，在第 2 段会自动指向门店照。这就是「不同分段不同素材」
能无痛接入的原因 —— 不用重写提示词模板。

## 三、每段素材怎么指定

`timeline_data` 里：

```jsonc
{
  "images": [                       // 全局素材箱（放所有图）
    {"id":"main", "file":"video/S06_still.png", "name":"S06_still.png", "width":1088,"height":1920},
    {"id":"shop", "file":"video/S06_mat_shop.jpg", "name":"门店.jpg", "width":1088,"height":1920}
  ],
  "segmentConfig": {
    "count": 3,
    "mode": "timeline",
    "segments": [
      {"startFrame":0,   "endFrame":122, "images":["main"],        "audios":["aud"], "prompt":"…"},
      {"startFrame":105, "endFrame":227, "images":["shop"],        "audios":["aud"], "prompt":"…"},
      {"startFrame":210, "endFrame":332, "images":["main","shop"], "audios":["aud"], "prompt":"…"}
    ]
  }
}
```

`images` 里放的是 **id（字符串）**，不是下标。源码 `_ordered_segment_assets()`：
按 id 匹配、按给出顺序排列、去重。

### ⚠ 三个必须记住的坑

1. **段里的 `images` 为空 / 缺失 = 这一段没有参考图**，不是「用全部图」。
   → 变相文生视频，脸会崩。所以**每一段都必须显式列出 images**。
2. **`id` 必须全局唯一**，且与 `file` 同时存在，否则 `by_id` 里根本查不到。
3. **超过 9 张的会被静默丢弃**（`image_ids = image_ids[:MAX_REF_IMAGES]`），
   不报错。所以别指望「多传几张让它挑」。

## 四、上限（源码常量，不是网页抄的）

```python
MAX_REF_IMAGES       = 9      # minimax_h3_timeline_director.py:48
MAX_REF_VIDEOS       = 3      # :49
MAX_REF_AUDIOS       = 3      # :50
MAX_REF_VIDEO_SECONDS= 15.0   # :51
```

`docs/AGENT_LONG_VIDEO_GUIDE_CN.md` 补充的一条（README 里没写）：

- 单次输出 **4–15 秒**，24 FPS
- 参考视频每段 2–15 秒，**视频参考总时长不超过 15 秒**
- **所有类型参考文件合计最多 12 个**

## 五、提示词六段式（字段名不可改、不可换序）

```
subject_definitions:
summary:
retention_analysis:
detailed_description:
overall_soundscape:
non_diegetic_music:
```

英文书写；对白、歌词和画面中可见文字保留原语言。
（与我们已经落地的 H3 骨架一致，见 `docs/提示词规范-H3与QwenImage21.md`。）

## 六、长视频分段的三条硬规矩（Agent 规范 §4）

1. **下一段的 `[Shot 1]` 必须先复述固定 Guide 里已有的画面**，不能直接写新剧情 ——
   否则提示词与固定画面冲突，新描述失效。
2. `[Shot N]` 是**每次生成内部的局部编号**，跟全片镜头号不是一回事，要自己维护映射。
3. 重叠取上一段最后 **1–2 秒**，别机械固定 2 秒；不要把重叠边界放在嘴型中间
   或快速闪切中间。

## 七、落到我们流水线的形态

新增 **`05_文案/<套次>/materials.json`**（跟 prompts.json 同级）：

```jsonc
{
  "set": "S06_xxx",
  "images": [
    {"id":"main", "file":"02_素材真值/洁斌_形象底图_1088x1920.png", "note":"默认静帧"},
    {"id":"shop", "file":"02_素材真值/S06_xxx/门店.jpg", "note":"客户给的新素材"}
  ],
  "segments": {
    "2": ["shop"],             // 第2段（1 起数）用门店照
    "3": ["main", "shop"]
  }
}
```

- 没这个文件 → 行为跟今天完全一样（只有 `visual.still` 那一张）。
- `segments` 里没写的段 → 自动用 `["main"]`，**不会变成无参考图**（针对坑 1 的护栏）。
- 素材路径必须在**本 IP 目录内**，跨 IP 直接 exit 1（防把上一位客户的脸/门店
  串到下一位客户身上）。

环境变量：`MATERIALS=<materials.json 绝对路径>`。

## 八、2026-10-30 真跑实测（别只信代码，这是跑出来的）

条件是：同一条音频、同一个 seed（20261030）、同一套英文骨架提示词，
**只改第 2 段的参考图** —— 第 1/2 段以外的段全用起始静帧（洁斌）。

| 段 | 挂的参考图 | 结果 |
|---|---|---|
| 段1 | 洁斌起始静帧 | 洁斌本人，米色 lounge |
| **段2** | **老王形象底图**（灰白头发老者 + 砖墙） | **出来就是那位老者** |

结论：

1. **模型真的按段取图**，不是「只认第一张」。
2. `<Picture 1>` 段内重编号成立 —— 骨架里写死的 `<Picture 1>` 在第 2 段
   自动指向新素材，**提示词模板一个字没改**。
3. ★ **但服装和背景跟着提示词走，不跟素材。** 段2 的脸是老王，
   身上却是骨架描述的「白色对襟衫 + 领夹麦」，背景仍是米色墙 ——
   因为骨架里 `$appearance` / `$scene_role` 这些变量写得很具体。
   **想让服装/背景也跟着换素材，必须同时改 `ip.json` 的 `prompt_vars`
   或那一段的 `prompts.en.json`，光换图不够。** 这是最容易「以为改了」的坑。

同时修掉的两个真 bug（这两个以前一直在，只是没人踩）：

- **PILOT=指定段号根本提交不了**：插件硬校验「第 1 段必须从第 0 帧开始」，
  而 PILOT 只截取第 N 段、起始帧不为 0 → ComfyUI 直接拒
  `Segment 1 must advance in time without gaps`。现在把时间窗平移到 0 起、
  音频用 `trimStart` 取对应那段，实测 45s 出 5.17s（正是段2 长度）。
- **PILOT=指定段号用的是第 1 段的提示词**：`build_prompt(i, ...)` 的 `i`
  在截取后的列表里从 0 重新数 → 命中「段1 的缓推镜头」和 `prompts.en.json`
  的第 1 段。于是「只测末段看劣化」测出来的是「段1的提示词 + 末段的时间轴」，
  等劣化永远等不到。现在提示词/素材索引用绝对段号。

### 参考视频路线真跑实测（同一天第二组）

- DRY 落点正确：段 2 的 `videoClips` = `start 7.0833`（正是切点）、
  `duration 7.2917`（正是段长）、`referenceMode: "edit"`、`trimStart 0`。
- 真跑被插件接受（日志 `参考视频 v1（edit） 7.0833s 起、7.2917s`），
  **出片人物与构图确实跟参考视频一致** —— edit 在驱动画面，不是占位参数。
- ★ **参考视频不能带任何字。** 这次图省事拿「字幕版成片」裁了 8 秒当参考，
  结果 raw 画面里出现了**模型自己画出来的字幕**（位置跑到画面顶部，跟参考视频的底部位置不同），
  再叠一层正式字幕 → **双层重影**（10s 处一眼可见）。
  更麻烦的是：**它不认「这段没挂视频」** —— `segmentConfig` 每段里根本没有视频字段，
  `videoClips` 只有顶层一条带 `start/duration` 的轨道，所以第 1 段（0–7.29s，没被指定用视频）
  的 raw 里同样冒出了字。结论：参考视频里有字/水印/台标，整片都会被污染。
  已在出片日志加固定提醒；找素材一律要**原始无字**的版本。
- 顺带修掉同一病根的另一处：`prompts.en.json` 的段号 `i` 从 **1** 起，
  而 `build_prompt(i)` 的 `i` 从 **0** 起 → 每段都取到上一段的分镜、末段的分镜永远用不上。
  上面「八」记录过素材索引的同类问题，分镜索引这处当时漏了。
  现在统一 `+1`，并加了「段号出现 0 就拒绝出片」的护栏（错位的画面看着也像在讲，最难查）。
