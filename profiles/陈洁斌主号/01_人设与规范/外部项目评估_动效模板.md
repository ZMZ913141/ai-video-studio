# 两个外部视频项目评估（2026-10-27）

评估对象：
1. https://github.com/adunext/adu-motion-video
2. https://motiongit.com/templates?cat=talk

**一句话结论：定位不匹配，不接入。但从中挖到 3 条真有用的工程经验，
其中 1 条直接命中我们未来的坑。**

---

## 一、它们是什么

| | adu-motion-video | motiongit talk 模板 |
|---|---|---|
| 定位 | AI 助手驱动的**动效模板包**（`.motion` 格式） | 模板分发站（同一作者的内容站） |
| 技术栈 | HTML/CSS/JS 浏览器渲染 → 逐帧截图 → ffmpeg 合成 | 同左，只是分发 |
| 输入 | 口播文案 + 素材（音频/录屏/图片/配乐） | 同左 |
| 输出 | MP4 + 可编辑工程 | 同左 |
| 风格 | 6 大类（现代图文/纸面透视/深色3D/科技控制台/鲜色角色/活力色彩），横竖屏 | 14 个模板 |
| 许可 | MIT | 部分免费、部分「达到目标后免费」 |

**它们的核心产品是「动效编排」** —— 大量图形元素、转场、分屏、节拍字效。
本质是把「AE 手动调关键帧」换成「参数化代码模板 + AI 填内容」。

## 二、为什么对我们不适用（明确不采用）

我们的号是**固定机位人像口播**：
- 一个静帧 + 一段定版音频 → H3 生成说话视频
- 后处理只有：配乐混音 → v7 曝光曲线 → 烧字幕
- 画面里**没有第二个图形元素**，没有转场，没有分屏

而 adu-motion-video 的整套价值建立在「画面里要有大量动效」。
我们要用它的模板，等于**换掉整个内容形态**——从「真人说话」变成「图文动画」。
那不是优化，那是另一个号。

**技术栈也对不上**：它是浏览器渲染（Node 22 + Chromium headless + FFmpeg），
我们是 ComfyUI + H3 采样器 + libass 烧字幕。两套渲染管线没有交集。

⇒ **不安装、不接入、不引入 Node/Chromium 依赖。**

## 三、真正吸收的 3 条（按价值排序）

### ★★★ 1. 「帧号是唯一坐标」—— 这条直接命中我们未来的坑

规范原文（motiongit `.motion` spec）：

> Frame rate uses positive integer `num/den` to avoid floating-point ambiguity.
> **The host computes `t = frame × den / num`.**
> Legacy `window.seek(t, inputs)` receives seconds.
> **Never confuse seconds with integer frames.**

它的做法：**所有图层只接收整数帧号，秒值由宿主统一换算**，
且渲染必须「可随机访问」（第 120 帧的内容不能取决于是否播到了第 120 帧）。

**为什么这对我们重要 —— 我们已经有这个隐患了**：

我们的时间轴同时存在**三套单位**：

| 环节 | 单位 | 例子 |
|---|---|---|
| SRT / ASS 字幕 | 秒（毫秒精度） | `00:00:12,080` |
| `gen_video.py` 分段 | **帧**（整数，且必须是 `17n` 格点） | `c_i = 153 / 323 / 442` |
| `cut_quality()` 容差 | 先给秒 `tol=0.25`，再乘 FPS 变帧 | `round(tol * FPS)` |
| 烧字幕 `-ss` | 秒 | ffmpeg 参数 |

目前没出事，是因为 24fps 正好是整数、且我们只在 24fps 下出片。
**但只要哪天出现非整数帧率**（29.97 / 23.976，短剧/平台投稿常见），
「秒 ↔ 帧」的换算误差会**逐段累积**，落到接缝上就是音画不同步。

**落地建议（现在不做，写进待办）**：
- 现状：`FPS = 24` 是唯一基准，`ts()` 用 `f"{int(sec//60):02d}:{sec%60:06.3f}"` 直接格式化秒 → 无累积误差，安全
- 触发条件：一旦要出 29.97/23.976，**必须先**引入「整数帧号唯一坐标」，
  全链路只用帧号，秒只在最终 ASS/ffmpeg 边界换算一次
- 判据：任何地方出现「秒 → 帧 → 秒」往返，就是 bug 温床

> 这条属于「**别人踩过、我们即将踩**」的经验，价值最高。
> 我们没有采纳它的代码，但采纳了它的**约束**。

### ★★ 2. 「长文案不许缩字号硬塞，必须分段/分页/换场」

规范原文：

> Long text, larger lists, changed data or missing media SHOULD trigger
> **segmentation, pagination, scene changes or explicit capacity feedback**,
> not unreadable scaling or cropped information.

**对我们的直接映射**：字幕**绝不为了一行塞下而缩字号**。
S03 那次「字幕字号 44→48」的调整正是反例思路 ——
当时是先定字号再折行，正确顺序是**先按语义断句、再按字号折行、实在放不下就拆 cue**。

已落地的对应做法：`make_srt_asr.py` 按**定稿标点**切 cue（语义优先），
`--maxline 12` 只控制折行，不控制 cue 数量。✅ 已符合。

### ★ 3. 「切点容差必须显式且统一」

规范要求帧率用有理数、渲染确定性，本质是**同一个量不能有两套标准**。

这条我们**刚踩过**：`cut_quality(tol=0.25)` 是 ±6 帧，
而 `pause_energy.py` 默认 ±2 帧，同一个切点两个工具结论相反。
已于 2026-10-27 统一到 `SEG_CUT_TOL=6`，并留 `SEG_CUT_TOL=2` 做严格档。

⇒ 已解决，此处仅记录「外部项目也强调同一件事」，作为佐证。

## 四、明确不采纳的部分（附理由，避免以后重复评估）

| 特性 | 不采纳理由 |
|---|---|
| `.motion` 模板格式 | 需要 Node 22 + Chromium headless，我们是 Python/ComfyUI 栈 |
| 6 大风格动效库 | 我们是固定机位人像，画面里不加图形元素 |
| 场景包（Scene Packs） | 那是多镜头编舞，我们单镜头一镜到底 |
| 「受保护适配」护栏 | 我们的等价物是 `gen_video.py` 的 `validate()` 硬约束，已更强 |
| 字体回退 + 排版校验 | 我们已用 `fontsdir` 锁死 7 个字体，且 `burn_ass.py` 会显式给目录 |
| 右上角「时间 + Logo」角标 | 与号的人设不符（素人感 vs 栏目感） |
| 共享输出时钟 | **概念已吸收**（见上文第 1 条），但不引入其实现 |

## 五、结论

- **不安装、不引入依赖、不改渲染链路**
- 吸收 3 条工程约束，其中「帧号唯一坐标」写入待办，等真要出非整数帧率时执行
- 这个项目本身做得不错，但它解决的是「**动画型**短视频」，
  我们做的是「**真人型**口播」。**形态不同，工具不可迁移。**

## 附：评估方法备忘

这类项目值不值得看，用三个问题快速筛：

1. **它画的是真人还是图形？** —— 真人 ← 我们是这条，图形型工具全部不适用
2. **它管的是「生成」还是「编排」？** —— 它管编排，我们管生成，不重叠
3. **它的时间基准是秒还是帧？** —— 只要它认真谈了帧/有理数/确定性，
   哪怕不采用代码，**它那一层工程纪律值得抄**
